# Foundry Local RAG Assistant

A local, offline Q&A assistant that answers questions about Foundry Local by
retrieving relevant passages from a small knowledge base and generating
answers with a local LLM — no cloud calls, no API keys, nothing leaves the
device. Built as a week-by-week learning project following
[Building Your First Local RAG Application with Foundry Local](https://techcommunity.microsoft.com/blog/azuredevcommunityblog/building-your-first-local-rag-application-with-foundry-local/4501968)
and Microsoft Learn's Foundry Local documentation.

## Problem it addresses

General-purpose LLMs either don't know about a specific, narrow topic or
"hallucinate" a plausible-sounding but wrong answer. This project grounds
answers in a fixed, local knowledge base instead: if the answer isn't in the
documents, the assistant says so rather than guessing — and it works fully
offline, which matters for privacy-sensitive or disconnected environments.

## How it works (RAG pipeline)

1. **Ingestion** — documents are split into passage-sized chunks, each chunk
   is embedded (turned into a vector) by a local embedding model, and stored
   in a local SQLite database alongside its source name.
2. **Retrieval** — when a question comes in, it's embedded the same way, then
   compared (cosine similarity) against every stored chunk to find the most
   relevant ones.
3. **Generation** — the retrieved chunks are inserted into a system prompt
   that instructs a local chat model to answer *only* from that context, and
   to say so honestly if the context isn't enough. If even the best chunk is
   a weak match, the model is skipped entirely and a fixed "I don't have
   that" answer is returned instead (see `MIN_RELEVANT_SCORE` below).

```
question ──▶ embed ──▶ compare against rag.db ──▶ top-K chunks
                                                        │
                                         weak match? ───┴──▶ fixed "I don't
                                                             have that" answer
                                                        │
                                                        ▼
                                     system prompt + chunks + question
                                                        │
                                                        ▼
                                              local chat model
                                                        │
                                                        ▼
                                    answer, citing its source inline
```

Everything runs through [Foundry Local](https://learn.microsoft.com/azure/ai-foundry/foundry-local/),
which handles downloading, caching, and running the models on-device
(CPU/GPU/NPU, whatever's available).

## Project structure

| File | Purpose |
|---|---|
| `main.py` | Week 1-2: the whole idea in one file — a hardcoded document list, embeddings and similarity search in memory, no database. Nothing else imports it, so it stays safe to read and experiment with. |
| `sqlite_practice.py` | Week 2: standalone SQLite mechanics practice (create table, insert, query by id and by keyword). Nothing imports it — it's the exercise that preceded the real pipeline. Writes `practice.db`. |
| `ingest.py` | Week 3: chunks documents (`chunk_text()`), embeds them, and persists them (with a `source` name) to `rag.db`. Run this first. |
| `retrieval.py` | Week 3: `get_top_chunks(query, ...)` — the SQLite-backed retrieval function, reused by both interfaces below. |
| `app.py` | Week 4-5: `answer_query()` (retrieval + local chat model) plus a CLI (`Question: ` prompt loop). The main way to run the assistant. |
| `web_app.py` | Week 5 stretch goal: a Flask server exposing `answer_query()` over a `/ask` JSON endpoint. |
| `templates/index.html` | The (intentionally basic) HTML+JS page served by `web_app.py` — a text box, a button, and an answer area. |
| `test_suite.py` | Week 5: an automated test harness — runs a fixed set of answerable/unanswerable/general questions through `app.py`, checks the responses, measures timing, and writes `test_results.md`. |
| `test_results.md` | Generated by `test_suite.py` — latest test run's pass/fail table, performance notes, and self-critique. |
| `requirements.txt` | Python dependencies (`foundry-local-sdk`, and `flask` for the web UI). |
| `rag.db` / `practice.db` | SQLite databases (generated, not hand-edited — `rag.db` by `ingest.py`, `practice.db` by `sqlite_practice.py`). |

## Setup

Requires Python 3.10+.

```bash
pip install -r requirements.txt
```

Foundry Local itself (the runtime that downloads and runs the models) needs
to be installed separately — see
[Get started with Foundry Local](https://learn.microsoft.com/azure/ai-foundry/foundry-local/get-started).
The first run of `ingest.py` or `app.py` will download the embedding model
(`qwen3-embedding-0.6b`) and chat model (`phi-3.5-mini`, ~3.8B params) the
first time they're needed — this can take a while depending on your
connection; after that they're cached locally.

## Usage

**1. Build the knowledge base (run once, or after changing the documents):**

```bash
python3 ingest.py
```

This embeds the documents in `ingest.py` and writes them to `rag.db`,
printing a count so you can verify nothing silently failed. `rag.db` is
generated (and gitignored), so a fresh clone always needs this step first —
`app.py` and `web_app.py` check for it up front and tell you to run this if
it's missing, rather than failing later on your first question.

**2. Ask questions, either from the terminal:**

```bash
python3 app.py
```

or from a browser, via the Flask web UI:

```bash
python3 web_app.py
# then open http://127.0.0.1:5000
```

Both interfaces call the same `answer_query()` function in `app.py` — the
retrieval and generation logic is identical, only the input/output changes.

**3. Run the test suite** (loads the models, runs a fixed set of test
questions, writes `test_results.md`):

```bash
python3 test_suite.py
```

## Design decisions & known limitations

- **Brute-force retrieval.** `retrieval.py` pulls every row out of SQLite and
  computes cosine similarity in Python rather than using a real vector
  database or a SQL-level distance function. This is fine for the handful of
  documents here; it would need to change (FAISS, a vector DB, or a SQL
  extension) at real scale.
- **Chunking is minimal.** `chunk_text()` splits on blank-line paragraph
  breaks — good enough for the one demo document included, but a real
  document set would likely need smarter splitting (sentence-aware, overlap
  between chunks, size limits).
- **Embeddings stored as JSON text**, not a binary blob or a dedicated vector
  type — SQLite has no native vector type, and JSON keeps the schema
  readable for a learning project. A blob would be more compact at scale.
- **Citations are prompt-written, but verified in code.** The system prompt
  asks the model to cite the source it used ("according to Foundry Local
  FAQ, …"), using only the names shown in its context. That's a claim, not a
  guarantee — small models can invent a plausible-sounding source. So
  `cited_sources()` in `app.py` compares the names in the answer against the
  chunks actually retrieved, and `test_suite.py` reports any citation that
  doesn't match as fabricated rather than counting it as cited. In the
  latest run, 5/5 grounded answers cited a real source and none were
  fabricated.
- **An earlier attempt at this failed, and the reason is worth knowing.**
  Before the similarity threshold existed, prompt-based citation was
  unreliable: the model would attach a source to an "I don't know" answer,
  or invent one, because it was being handed weak, irrelevant context and
  asked to work with it anyway. Fixing retrieval (below) removed that
  situation entirely — the model now only ever sees context worth citing —
  and the same prompt approach started working. The lesson was that the
  citation bug was a *retrieval* bug wearing a prompt-shaped mask.
- **Similarity threshold guards against weak retrieval.** A real test with a
  non-English, off-topic question (`"bu gece hava kaç derece"` — Turkish for
  "what's the temperature tonight") showed the failure mode plainly: with
  only weak/irrelevant chunks retrieved, the model produced garbled,
  hallucinated text instead of a clean decline — because our "say you don't
  know" instruction is written in English and doesn't reliably transfer to
  a non-English response. Fixed with `MIN_RELEVANT_SCORE` in `app.py`: every
  retrieved chunk is filtered against the threshold, and if none survive the
  chat model isn't called at all — a fixed fallback answer is returned
  directly. This is language-independent, faster (skips a model call), and
  is now a permanent regression test in `test_suite.py`.
- **The threshold filters per chunk, not just the top one.** `top_k` caps how
  many chunks come back; it doesn't promise they're all relevant. A query can
  pull one strong match and one weak filler, and testing only the best score
  would let that filler ride into the prompt — which is precisely the
  low-relevance context that caused the hallucination above. With the current
  11-chunk knowledge base this never triggers (all chunks are about the same
  subject, so their scores cluster within ~0.15 of each other and pass or fail
  together), but it will the moment the knowledge base grows or diversifies.
  Verified by raising the threshold between two real scores and confirming
  only the stronger chunk reached the model.
- **Empty-input handling.** The CLI reprompts on a blank Enter instead of
  exiting; only typing `quit` ends the session (see `test_results.md` for
  how this was tested).
- **Generated files are not versioned.** `rag.db` and `__pycache__/` are in
  `.gitignore` — the database is rebuildable at any time with `ingest.py`,
  so only the code and documentation are tracked in git.
